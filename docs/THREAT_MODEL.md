# Threat model

Regtest only. Not audited. The labels below are the author's, not a third-party severity. Two officers who agree can spend. That is the policy, and it is out of scope to prevent.

The guard for money is the Bitcoin script, checked by bitcoind. The officer's device is the guard for "this is the payment I was asked to sign." The coordinator is watch-only. A screen is not a guard, and this repository has no screen.

## Attacks

| Attack | What the attacker does | What stops it | What remains |
| --- | --- | --- | --- |
| Dishonest treasurer | O1 builds a spend to their own address and signs once. | Path A needs a second officer key. bitcoind rejected a one-signature witness with `NULLFAIL` (`pnpm kill-test`, `pnpm e2e`). | O1 plus O2, or O1 plus O3, can spend. The product does not detect that they agreed in private. |
| Malicious coordinator | The server swaps the recipient, the amount, or the change output inside the PSBT after the request was read. | The officer re-derives the scripts from xpubs stored on the device and refuses with `PSBT_MISMATCH` before signing (`pnpm tamper-test`). Change to any other address fails the same check. | A modified officer client can skip the check. The script still requires two signatures. The server can also refuse to store a legitimate request. That is a denial of service, not a spend. |
| Coordinator holds no key, and must not grow one | Someone asks the server to sign, or to store an xprv "for recovery." | No request path reads a private key. Officer keys are encrypted on the device with PBKDF2-SHA256, 310,000 rounds, and AES-256-GCM. A file that claims fewer rounds is refused. | The host that runs the coordinator can still be rooted. That grants the database and the watch-only xpubs. It does not grant a signature. |
| Lost officer key | One of O1, O2, O3 loses the seed. | The other two can still spend on path A. | If two seeds are lost, path A is dead. Path B needs the assembly seed and one surviving officer, and only after N blocks. Losing the assembly seed as well leaves the coins unspent. There is no fourth path. |
| Lost device | The phone is stolen. The key file is on it. | The file is ciphertext. A wrong pin fails. The pin is not on the server. | A weak pin can be guessed offline. Eight characters is the minimum the CLI enforces, not a strength proof. The thief does not get a second officer's key from this file. |
| Relay spam or a forged request | Anyone can publish to the demo relay. A gift wrap is addressed to an officer. | The officer ignores unknown types. A message whose `coordinator_url` is not the officer's configured coordinator is ignored and the PSBT is not fetched. An expired message is ignored the same way. The approval they send back carries no PSBT. | The demo relay does not authenticate publishers. A public relay has not been used. Spam can fill the relay. It cannot satisfy the script. A stolen Nostr key can send a message that looks like that officer. The bitcoin signature is a different key. |
| Replayed officer auth | The same `Authorization` header is sent twice. | The signature covers method, path, timestamp, nonce, and the raw body. The timestamp must be within five minutes. The nonce is stored and consumed before the business write. A replay is `VALIDATION`. | The nonce store is SQLite on one process. A second coordinator with a copy of the database that has not yet seen the nonce is not a setup this repo has run. |
| Replayed spend | The same two signatures are broadcast again. | bitcoind will not accept the same inputs twice. The coordinator marks the request broadcast and keeps the coins reserved until the scan sees them spent. | A failed broadcast releases the coins and does not retry. The officers must create a new request. That release was a choice so a stuck request cannot freeze the fund. A bug in "failed" could release coins that actually broadcast. The receipt is the txid plus the later ledger line, not the HTTP status alone. |
| Rate manipulation | The price URL returns a EUR figure the attacker chose, or no figure. | Sats are locked at request creation and rounded up. Officers approve that sats number, not a fresh quote. No cache and a failed fetch is `RATE_UNAVAILABLE`, not a default. A cached price older than 60 seconds is served with `stale: true`. `require_fresh=1` refuses that with `RATE_STALE`. | The coordinator trusts whatever `MEMPOOL_PRICES_URL` returns. The demo points it at a fixture of 60,000 EUR and says so. A hostile fixture can lock an absurd sats amount. The officers still see that amount before they sign. Regtest sats have no value either way. |
| Log leakage | A log line contains a name, a phone, a seed, a PSBT, an `nsec`, a pseudonym, a purpose, or a reject reason. | The coordinator redacts the body and the `Authorization` header. The audit row stores amounts, path, status, and txid. It does not store the purpose or the reason. The reason stays on the request row. `pnpm e2e` scanned the coordinator log and the command output. | Phones are not collected, so their absence is not a hard scan. The container log scan has not been run. A future UI must not put the purpose in a URL. |
| Database tamper | Someone edits an audit row, a balance, or the xpubs a member is shown. | The member's phone recomputes the SHA-256 chain from `GET /v1/funds/:id/audit` and checks spend signatures against the raw transaction. The link fragment is the hash of the four xpubs and the delay. `audit verify` on the server is the same chain function. Changing one row failed verification at seq 1 (`pnpm e2e`). | A chain rewritten from the genesis row still matches. The phone does not count blocks. Confirmations are the coordinator's number. The UTXO set in bitcoind is the balance. |
| Early recovery | One officer and the assembly key try to spend before N blocks. | The path B input sets `nSequence` to N. bitcoind returns `non-BIP68-final` until the coin is old enough. The coordinator also refuses to build that PSBT while the coin is young, so the HTTP API does not reach the early broadcast. The CLI `recover` command does, and bitcoind refused it. | N is chosen at fund creation. Regtest uses 10 so the demo can finish. A fund created with N = 10 on any network where blocks are fast has a short wait. About 4,320 is the figure for a real configuration, and it has not been used. |
| Collusion of two officers | O1 and O2 sign a payment the members did not want. | Nothing in this repository. | Stated plainly: 2 of 3 is the spend rule. The ledger shows the payment afterwards. It does not stop it. A third officer can veto only before broadcast. |

## What the server stores

Xpubs, member pseudonyms, addresses, the ledger, the request including its purpose and its PSBT, the reject reason, and the audit chain. It does not store a mnemonic, an xprv, an `nsec`, a pin, or a phone number.

The pseudonym is a label the member add sent. It is not authenticated. It is personal data relative to the log rule, which is why it must not be logged. It is still in the database, because the ledger has to show who contributed.

## Kept failure

On the first regtest run, a correct 2-of-3 witness was rejected because the earlier signature was stacked on top. CHECKMULTISIG pops the later signature first. The one-signature refusal on that same run was already right. The fix is in `packages/core/src/witness.ts`, dated 17 Nov 2026, and the old order is in the comment. A later green run does not delete that line. The record is also the first section of [DEFERRED.md](DEFERRED.md).
